# Audit run, Nov 17, 2026

I ran Cloudflare's open-source [security-audit skill](https://github.com/cloudflare/security-audit-skill) once against this repo. It's a coding-agent skill: isolated agents map the code, hunt in assigned areas, and a separate agent tries to disprove each finding.

**How much to trust this.** The run was source-only. There was no sandbox, so nothing was executed, and it used the skill's quick profile (one verifier per finding, no second pass). I checked each finding against the source myself before fixing anything, and every fix has a test that fails without it (`test/audit-findings.test.mjs`, the attack journey, and mutants). One run finds only part of what repeated runs would, so this isn't a clean bill of health.

## Fixed

| Finding | What was wrong | Fix |
| --- | --- | --- |
| Reconciliation report and transfer request skipped the read scope | Someone outside a restricted item's audience could learn who its steward and contributors were, and that it existed | Both routes now refuse a reader outside the audience |
| Forking a restricted item | A fork copies the SEE text into a new item that has no audience, so it would hand private text to the whole workspace | Outsiders are refused, and restricted items can't be forked at all until a fork can inherit the audience. Since Nov 26, 2026 it does: a fork or renewal carries its parent's audience exactly, and the store refuses any other (`test/restricted-fork.test.mjs`) |
| Contribution record ignored audiences | Anyone could see ids, kinds and hashes of restricted work through a person's page (metadata only; the records themselves stayed refused) | The record now applies the same audience filter as Search |
| Inbound integration rate limit never refused | An async check was not awaited, so a Promise was always truthy. It needed a valid signing secret to reach | Awaited |
| Workspace research could copy restricted text into a wider item | With in-workspace research on (off by default), a steward who sits in a restricted group could pull its text into an item everyone can read | Sources are filtered by audience, the same rule reanalysis already uses |

## Second pass and a hostile browser pass

I ran the skill a second time on the areas the first run skipped (the builder worker, mentoring, reanalysis, the gateway lanes, the SSRF guard, the database layer and more), and wrote an attack journey that drives a real browser and real HTTP against a running server (`npm run test:attack`, also in CI). It signs in four people, makes a restricted item, and then tries to read it from every route, forge authority, post from another site, frame the app, inject script, break out of a hostile delivered try, send oversized and malformed input, and race single-use things.

| Finding | Where it came from | Fix |
| --- | --- | --- |
| **The home feed showed a restricted item's text to everyone.** The JSON list filtered by audience and the page didn't | Found by the attack journey, then confirmed by the second audit pass | The page filters the same way |
| Renewing a restricted item copied its text into an open item (the sibling of the fork problem) | Second pass | Refused, like fork |
| Steward-only routes (research, spec draft, send, steer, deliver a try) skipped the read check, so a steward who had left the audience could still act on the item | Second pass | One read check in front of all of them |
| A failed model call kept a concurrency slot forever, so one run's failing calls could starve every other run | First and second pass | The spend hold stays until an operator releases it, but the slot frees once the call's timeout has passed |
| Erasing wording didn't reach a model-built bundle that had copied it (files are base64 inside JSON), and an erased artifact was still served | Second pass | Erasure decodes bundle files, and erased artifacts are not served |
| The agent manifest was read with no size cap and followed links, so a planted link could hang the worker (codex profile) | Second pass | Same bounded, no-follow read the HTML output already uses |
| The chat gateway didn't check message parts, so an image or audio part could cost more than its bytes reserved | Second pass, needs-validation | Only text parts are accepted |
| The Quest gateway's shared cap left out analysis spend (about $0.10 per person per day) | Second pass | Counted |
| The bundle origin looked up artifacts with a `LIKE` scan before checking the signature | Second pass, needs-validation | An indexed range lookup (checked with `EXPLAIN QUERY PLAN`) |

What the attack journey checked and found holding: CSRF tokens and origin checks, SameSite and HttpOnly cookies, session fixation, forged and logged-out cookies, a spoofed `X-Forwarded-For`, open redirects, clickjacking, cross-site fetches and form posts, about 70 injection and path-traversal and verb and size cases, 12 parallel redemptions of one invite, and a hostile try that attempted to read cookies, the parent page, the app's API and the network, and to navigate the top page, pop a window and fake a Helps vote. Everything was contained.

## The three left open, now done

- **Erasing a SPEC now reaches forks that copied it.** The copied lines are blanked in the fork's first event, and the fork gets its own erase record so every hash chain still verifies. Only forks of that exact SPEC are touched. A fork in a final state can't take the record and is counted as "unreached" in the erase response.
- **Reanalysis updates are re-checked when read**, so a later group change can't expose text quoted from a source the new readers couldn't see.
- **The builder's work folder has a size and file-count budget** (32 MiB, 2,000 entries). The host checks it while the build runs and kills the container if it goes over. A separate size-limited volume is still good practice (`docs/DEPLOY.md`).

## Not covered

After two quick-profile passes, little or no coverage remains for: the `scripts/` and `demo/` folders, the body of the Vision Quest client code, the Investigate (`intelligence/`) code beyond how reanalysis calls it, the Postgres driver contract, the legacy item path, the Effort scheduler, the container images' contents (the Dockerfiles were read and the images are scanned by Trivy, but not built and attacked here), and how the digest page renders annex content. Nothing was run, so deployed TLS, proxy, identity provider and model behavior are untested by this.

## What held

CSRF, sessions, step-up and login lockout; OpenID Connect sign-in; the role and independence rules in the state machine; the gateway's cap arithmetic; the builder container flags and bundle checks; HTML escaping.
