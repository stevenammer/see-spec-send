# Audit run, Nov 17, 2026

I ran Cloudflare's open-source [security-audit skill](https://github.com/cloudflare/security-audit-skill) once against this repo. It's a coding-agent skill: isolated agents map the code, hunt in assigned areas, and a separate agent tries to disprove each finding.

**How much to trust this.** The run was source-only. There was no sandbox, so nothing was executed, and it used the skill's quick profile (one verifier per finding, no second pass). I checked each finding against the source myself before fixing anything, and every fix has a test that fails without it (`test/audit-findings.test.mjs`, plus mutants). One run finds only part of what repeated runs would, so this isn't a clean bill of health.

## Fixed

| Finding | What was wrong | Fix |
| --- | --- | --- |
| Reconciliation report and transfer request skipped the read scope | Someone outside a restricted item's audience could learn who its steward and contributors were, and that it existed | Both routes now refuse a reader outside the audience |
| Forking a restricted item | A fork copies the SEE text into a new item that has no audience, so it would hand private text to the whole workspace | Outsiders are refused, and restricted items can't be forked at all until a fork can inherit the audience |
| Contribution record ignored audiences | Anyone could see ids, kinds and hashes of restricted work through a person's page (metadata only; the records themselves stayed refused) | The record now applies the same audience filter as Search |
| Inbound integration rate limit never refused | An async check was not awaited, so a Promise was always truthy. It needed a valid signing secret to reach | Awaited |
| Workspace research could copy restricted text into a wider item | With in-workspace research on (off by default), a steward who sits in a restricted group could pull its text into an item everyone can read | Sources are filtered by audience, the same rule reanalysis already uses |

## Reported, not fixed

- **A failed model call can leave a spend hold that never clears.** If the upstream provider rejects a call, the hold stays "dispatched" until an operator releases it, and concurrency is counted across all runs. A builder holding a run capability might use this to starve other runs. Not verified by running it, and the design may be intentional (see the threat model). Worth a look in the next slice.
- **Erasing a SPEC doesn't reach text already copied into a fork.** The fork's first event is non-erasable by design. Whether erasure should follow forks is a product decision.

## Not covered

The skill's quick profile deferred these, so no one has looked at them under this audit: the builder policy and watchdog, the Codex adapter, mentoring, reanalysis, the gateway's non-chat lanes, the SSRF guard, knowledge and catalog code, the database and migration layer, the client-side quest storage, and the scripts and demo. Nothing was run, so deployed TLS, proxy, identity provider and model behavior are untested by this.

## What held

CSRF, sessions, step-up and login lockout; OpenID Connect sign-in; the role and independence rules in the state machine; the gateway's cap arithmetic; the builder container flags and bundle checks; HTML escaping.
